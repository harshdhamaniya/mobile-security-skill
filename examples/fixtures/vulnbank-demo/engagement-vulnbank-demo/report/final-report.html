Executive summary

No Confirmed findings resulted from this engagement. The adversarial exploitation panel reviewed two manifest-level issues and elevated both to Potential / High: an explicitly-set android:debuggable="true" (AND-MAN-001), and an exported, browser-reachable deep link into .ui.TransferMoneyActivity with no permission guard (AND-MAN-003). Both were held at Potential rather than Confirmed for the same structural reason: this fixture has no installable build or implementation code, so a specific, named open conditional (a possible release-build override for the first; a possible in-app re-authentication step for the second) could not be closed by either static or dynamic evidence. Four further manifest observations (an unguarded exported AccountProvider, an unrestricted allowBackup, a missing <uses-sdk>, and a full component inventory) were logged by the manifest specialist but deliberately not escalated to the panel for this walkthrough: a scoping choice, not an oversight (see Appendix C). Readers should treat the two Potential/High findings as the walkthrough's headline result, and the overall exercise as a demonstration of this skill's reporting discipline on a minimal artifact, not as an assessment of a real shipped product.

MAN-04, MAN-09

Description: .ui.TransferMoneyActivity is declared android:exported="true" with an intent-filter carrying action=VIEW, category=DEFAULT, category=BROWSABLE, and data android:scheme="vulnbank" android:host="transfer" (extracted/AndroidManifest.xml:24-33). No android:permission attribute exists on the activity, and no <permission> element is declared anywhere in the 42-line manifest. The <data> element declares only scheme/host with no path constraint, so any path/query appended to the URI still routes to this activity.

Attack path: Source: attacker crafts a vulnbank://transfer URI and embeds it in a web page, SMS, or chat link (or a second installed app builds an explicit/implicit Intent). Delivery: BROWSABLE routes a tapped link directly to the activity with zero access-control checkpoint. Sink: TransferMoneyActivity.onCreate()/onNewIntent() receives the Intent; whether this executes a transfer or merely opens a still-authenticated form is unverified: no implementation code exists in this fixture.

Evidence: Static: extracted/AndroidManifest.xml:L24-33, independently re-verified by the prosecutor and both skeptics. Dynamic: findings/dynamic-session-log.md: adb shell am start -a android.intent.action.VIEW -d "vulnbank://transfer" com.vulnbankdemo.app against device 84f7a024 returned Error: Activity not started, unable to resolve Intent; re-run with no explicit package returned the identical failure, confirming no app on that device claims the scheme at all.

Exploitation panel verdict: Two independent skeptic passes both returned "stands": neither found an attacker-model inflation, a missed sanitizer, an SDK-version default that rescues it, or a standard-behavior misread. Both independently named the same unresolved conditional: an in-app re-authentication/confirmation step between launch and an actual transfer, which no evidence in this record can confirm or rule out. Reachability alone is unambiguous here, but that open conditional on static-only evidence is Potential's definition, not Confirmed's. Full reasoning in exploitation/AND-MAN-003.md.

Remediation: Add a signature-level android:permission guard (or set exported="false" if no legitimate external caller needs it): the MAN-04 fix. Migrate the bare custom scheme to a Verified Android App Link (android:autoVerify="true" + assetlinks.json) to close the scheme-hijack angle: the MAN-09 fix. Enforce a fresh authentication/confirmation step in the activity itself before executing any transfer, regardless of manifest changes.

Ref IDs
MAN-01

Description: android:debuggable="true" is set as a literal, unconditional attribute on the <application> element (extracted/AndroidManifest.xml:10, inside the block spanning lines 7-13). No build-variant indicator, manifest-merger directive, or second manifest exists anywhere in the file to narrow or gate it.

Attack path: Source: the literal declaration. Platform effect: marks the app's UID debuggable, enabling root-free run-as UID switching and JDWP debugger attach from an authorized ADB session. Sink: full read/write of /data/data/com.vulnbankdemo.app/ via run-as, and/or a live JDWP attach capable of defeating any purely client-side check in memory.

Evidence: Static: extracted/AndroidManifest.xml:L7-13, independently re-verified by the prosecutor and both skeptics. Dynamic: findings/dynamic-session-log.md: adb shell run-as com.vulnbankdemo.app id against device 84f7a024 returned run-as: unknown package; cross-checked via pm list packages (no match among 389 packages) and dumpsys package (not found): the package has never been installed on the only available device.

Exploitation panel verdict: Both skeptic passes returned "stands," finding no release-build override, no manifest-merger directive, no SDK-version-gated default, and no basis to inflate/deflate the physical label. Nothing broke the chain, but the orchestrator still held this at Potential: the dynamic attempt proves run-as/JDWP was never exercised against a live process, and no build.gradle exists anywhere in the engagement to rule out a release-variant override forcing debuggable="false": a genuinely open conditional. Full reasoning in exploitation/AND-MAN-001.md.

Remediation: Set/confirm android:debuggable="false" for the release build type and verify no manifest-merger directive reintroduces it: the MAN-01 fix. The prosecutor's own attack-path analysis notes a live JDWP attach "allows bypassing any purely client-side check... because a debugger can single-step past or directly overwrite the result of any such check in memory": so no sensitive action (above all, money transfers) should rely solely on a client-side gate; pair the manifest fix with independent server-side re-verification of authentication/authorization state. (Note: resilience-anti-tamper-auditor itself was skipped for this engagement for lack of code/running app, so this client-vs-server framing is this report's own synthesis of the prosecutor's reasoning, not a verbatim carry-forward of that specialist's notes field.)

Description: .data.AccountProvider is declared android:exported="true" with authority com.vulnbankdemo.app.provider and no child elements at all (extracted/AndroidManifest.xml:35-38): no read/write/permission attribute, no <path-permission>, no URI scoping.

Attack path: Any installed app can issue a ContentResolver query/insert/update/delete against content://com.vulnbankdemo.app.provider with no permission held.

Evidence: Static: extracted/AndroidManifest.xml:L35-38. Dynamic: adb shell content query --uri content://com.vulnbankdemo.app.provider returned IllegalStateException: Could not find provider, confirming the provider is absent on-device because the package is not installed.

Why not Confirmed/Potential, what would upgrade it: Escalation to the adversarial panel to test the attacker-model/severity claims, plus the provider's actual implementation code (or an installed build) to determine what data is returned/mutated and whether raw-SQL injection via selection/sortOrder is possible.

Remediation: Add android:readPermission/writePermission (or per-path <path-permission>) tied to a signature-level custom permission; set exported="false" if no external app needs this data; confirm parameterized queries once implementation code exists.

Appendix C: Methodology & limitations

Phase 2 (static) specialist coverage. target-profile.md named three specialists to run: android-manifest-auditor (full remit), android-ipc-ui-auditor (scoped to manifest-level exposure of the two unguarded exported components), and deeplink-clipboard-auditor (scoped to its DLK-01..08 sub-check only). All six findings in findings/findings.jsonl are attributed solely to android-manifest-auditor: there is no record anywhere in this engagement of output from the other two recommended specialists; this report cannot determine whether they ran and found nothing to add, or did not run at all. The remaining ten specialists (ios-plist-entitlements-auditor, ios-platform-attack-auditor, storage-crypto-auditor, taint-flow-analyst, webview-security-auditor, oauth-oidc-auditor, resilience-anti-tamper-auditor, network-backend-auditor, supply-chain-framework-auditor, business-logic-auditor) were explicitly and deliberately skipped per target-profile.md, each because this fixture supplies only a plaintext manifest with no APK/AAB, DEX, source tree, or build.gradle for any of them to examine.

Phase 3 (dynamic) coverage. A real, connected, authorized Android device (84f7a024, Xiaomi Redmi "sweetin", Android 11/SDK 30, production build) was genuinely available and used, not merely assumed present (findings/dynamic-session-log.md). However, dynamic confirmation of actual app behavior did not occur for any finding, because there is no installable build of VulnBank: every proposed dynamic command (run-as, deep-link am start, provider content query, dumpsys package, adb backup) was executed verbatim and failed in the same consistent way (package/provider/activity not found), confirming the "no installable artifact" premise rather than confirming or refuting any manifest-level exposure claim. Hooking, fuzzing, MITM, resilience-bypass, and biometric-gate testing were not attempted: no running app process exists for any of them to target. The device's presence should not be read as implying full dynamic coverage for this target.

Phase 4 (adversarial panel) coverage. Only AND-MAN-001 and AND-MAN-003 were escalated to the full prosecutor/skeptic/orchestrator panel (exploitation/AND-MAN-001.md, exploitation/AND-MAN-003.md, two independent skeptic instances each). AND-MAN-002, AND-MAN-004, AND-MAN-005, and AND-MAN-006 were never escalated: a deliberate scoping choice for this demo, not an oversight; this report's fallback rule (use each finding's own severity_initial/status in place of a never-set final_severity) was applied to all four accordingly.

Tools actually used. adb (Android Debug Bridge version 1.0.41, Version 35.0.2-12147458) was used directly against the connected device for every Phase 3 command above. apktool, jadx, and aapt2 are present on the analysis machine's PATH but were not used, because the input artifact is a single plaintext, already-decoded AndroidManifest.xml with no binary AXML/DEX/compiled resources for them to operate on.

Out of scope per scope.md. Everything beyond AndroidManifest.xml review, explicitly: "Out of scope: everything else, since no real code exists for this fixture."
