# Mobile Application Security Assessment: VulnBank Demo (com.vulnbankdemo.app): manifest-only fixture

**Platform(s):** Android only (no iOS artifacts of any kind were provided)
**Engagement scope & authorization:** Own-app, author-authorized test fixture; see `scope.md`: "Target: VulnBank-Demo (com.vulnbankdemo.app), a synthetic manifest fixture authored for this repo's reproduction walkthrough... In scope: AndroidManifest.xml review (manifest-level findings only, this fixture has no actual source/DEX)."
**Assessment window:** 2026-10-08 to 2026-10-09
**Methodology:** OWASP MASTG-aligned static + dynamic analysis with adversarial exploitation confirmation (see Appendix C)

> **What this report actually is.** `VulnBank Demo` is a synthetic, hand-authored `AndroidManifest.xml` fixture (confirmed by its own `README.md`: "It is not a real app, not downloaded from anywhere, and not based on any specific published application... It intentionally contains a small number of well-known manifest misconfigurations... so the pipeline has something real to find."). There is no APK/AAB, no DEX, no source tree, and no `build.gradle` anywhere in this engagement. This report documents a genuine run of this skill's five-phase pipeline, including a real `adb` session against a real connected device, against that fixture, to demonstrate the pipeline end to end. It is **not** a production security audit of a real banking application, and its findings describe risk conditional on a real app ever shipping with this exact manifest, not a confirmed real-world incident.

## Executive summary

No Confirmed findings resulted from this engagement. The adversarial exploitation panel reviewed two manifest-level issues and elevated both to **Potential / High**: an explicitly-set `android:debuggable="true"` (AND-MAN-001), and an exported, browser-reachable deep link into `.ui.TransferMoneyActivity` with no permission guard (AND-MAN-003). Both were held at Potential rather than Confirmed for the same structural reason: this fixture has no installable build or implementation code, so a specific, named open conditional (a possible release-build override for the first; a possible in-app re-authentication step for the second) could not be closed by either static or dynamic evidence. Four further manifest observations (an unguarded exported `AccountProvider`, an unrestricted `allowBackup`, a missing `<uses-sdk>`, and a full component inventory) were logged by the manifest specialist but deliberately not escalated to the panel for this walkthrough: a scoping choice, not an oversight (see Appendix C). Readers should treat the two Potential/High findings as the walkthrough's headline result, and the overall exercise as a demonstration of this skill's reporting discipline on a minimal artifact, not as an assessment of a real shipped product.

## Potential findings (detailed)

### AND-MAN-003: TransferMoneyActivity exported with BROWSABLE custom-scheme deep link and no permission guard
- **Severity:** High **Attacker model:** remote (one realistic precondition: victim already has the app installed and taps/follows an attacker-supplied link, "remote delivery, one user tap," not zero-click) **MASVS:** MASVS-PLATFORM-1, MASVS-AUTH-1
- **Description:** `.ui.TransferMoneyActivity` is declared `android:exported="true"` with an intent-filter carrying `action=VIEW`, `category=DEFAULT`, `category=BROWSABLE`, and `data android:scheme="vulnbank" android:host="transfer"` (`extracted/AndroidManifest.xml:24-33`). No `android:permission` attribute exists on the activity, and no `<permission>` element is declared anywhere in the 42-line manifest: there is no signature-level gate even theoretically available to apply. The `<data>` element declares only `scheme`/`host` with no `path`/`pathPrefix`/`pathPattern`, so under Android's documented URI-matching rules any path/query appended to `vulnbank://transfer/...` still routes to this activity.
- **Attack path:** Source: an attacker crafts a `vulnbank://transfer` URI (optionally with extra path/query data) and embeds it in a web page, SMS, email, or chat link, or a second installed app builds an explicit/implicit `Intent(ACTION_VIEW, Uri.parse("vulnbank://transfer"))`. Delivery: because the activity is `BROWSABLE`, a tapped link in a mobile browser routes directly to it with zero access-control checkpoint (exported, no permission, no competing handler on the device). Sink: `TransferMoneyActivity.onCreate()`/`onNewIntent()` receives the attacker-influenced Intent/Uri; **this step is not backed by implementation evidence in this fixture**: no DEX/source/APK exists for this target, so whether reaching the activity (a) immediately executes a transfer, (b) opens a form still gated behind fresh authentication, or (c) something else, is inferred from the class name only, not confirmed.
- **Evidence:** Static: `extracted/AndroidManifest.xml:L24-33`, independently re-verified against the raw file by the prosecutor and both skeptics. Dynamic: `findings/dynamic-session-log.md`: `adb shell am start -a android.intent.action.VIEW -d "vulnbank://transfer" com.vulnbankdemo.app` against connected device `84f7a024` (Xiaomi Redmi "sweetin", Android 11/SDK 30) returned `Error: Activity not started, unable to resolve Intent`; re-run with no explicit package (bare implicit intent) returned the identical failure, confirming no app on that device currently claims the `vulnbank://` scheme at all. This confirms no installable build exists to exercise the sink; it neither confirms nor refutes the activity's actual post-launch behavior.
- **Exploitation panel verdict:** Two independent skeptic passes both returned "stands": neither found an attacker-model inflation (the prosecutor had already correctly kept `remote`, not `other-app`, since `BROWSABLE` requires no second app), a missed sanitizer (no `<permission>` anywhere in the manifest), an SDK-version default that rescues it (`exported="true"` is explicit, not defaulted), or a standard-behavior misread (this is exactly the MAN-04/MAN-09 anti-pattern, not a benign deep-link entry point like `LoginActivity`'s export). But both skeptics independently named the same specific, plausible, unresolved conditional: an in-app re-authentication or confirmation step between the activity launching and a transfer actually executing: something no evidence in this record can confirm or rule out, because no implementation code exists. Per the panel's severity-rating rule, reachability alone (unambiguous here) is not enough to reach Confirmed when a plausible conditional like this remains open on static-only evidence; that combination is Potential's definition, not Confirmed's. The orchestrator's full reasoning is in `exploitation/AND-MAN-003.md`.
- **Remediation:** Add a signature-level `android:permission` guard to the activity (or set `exported="false"` if no legitimate external caller needs to invoke it directly): the MAN-04 fix. Migrate the bare custom scheme to a **Verified Android App Link** (`android:autoVerify="true"` + a `assetlinks.json` Digital Asset Links file) to close the scheme-hijack angle a different app could otherwise register for: the MAN-09 fix. Regardless of manifest changes, the activity itself should enforce a fresh authentication/confirmation step before executing any transfer rather than trusting whatever extras arrive on the incoming Intent.

### AND-MAN-001: android:debuggable="true" set explicitly on &lt;application&gt;
- **Severity:** High **Attacker model:** physical (requires an already-authorized ADB session: USB debugging enabled and the host already authorized, or a prior wireless-ADB pairing; not "any physical access to any locked device, no questions asked") **MASVS:** MASVS-RESILIENCE-2
- **Description:** `android:debuggable="true"` is set as a literal, unconditional attribute on the `<application>` element (`extracted/AndroidManifest.xml:10`, inside the block spanning lines 7-13). No build-variant indicator, manifest-merger directive (`tools:replace`/`tools:node`), or second manifest exists anywhere in the 42-line file to narrow or gate it.
- **Attack path:** Source: the literal `debuggable="true"` declaration. Platform effect: this marks the app's UID as debuggable in the package manager, which (a) lets an ADB shell switch to that UID via `run-as` without root, and (b) causes the process to expose a JDWP endpoint that a standard debugger can attach to. Sink: an attacker with an authorized ADB session gets `adb shell run-as com.vulnbankdemo.app <command>` (full read/write of `/data/data/com.vulnbankdemo.app/`, bypassing sandbox isolation) and/or a live JDWP attach capable of single-stepping past or overwriting the result of any purely client-side check in memory.
- **Evidence:** Static: `extracted/AndroidManifest.xml:L7-13`, independently re-verified against the raw file by the prosecutor and both skeptics. Dynamic: `findings/dynamic-session-log.md`: `adb shell run-as com.vulnbankdemo.app id` against device `84f7a024` returned `run-as: unknown package: com.vulnbankdemo.app`; cross-checked independently via `pm list packages` (no match among 389 installed packages) and `dumpsys package` (`Unable to find package`). All three agree the package has never been installed on the only available test device, so the sink was never exercised against a live process.
- **Exploitation panel verdict:** Both skeptic passes returned "stands," each independently re-reading the full manifest and the entire engagement directory tree and finding no release-build override, no manifest-merger directive, no SDK-version-gated default (`debuggable` is never version-gated on any API level), and no basis to inflate or deflate the `physical` attacker-model label the prosecutor had already conservatively kept. Nothing broke the chain, but the orchestrator still held this at Potential rather than Confirmed for two concrete reasons: (1) the dynamic attempt above proves `run-as`/JDWP was never actually exercised against a live process, only attempted against a package that isn't installed; and (2) no `build.gradle` exists anywhere in this engagement to rule out a release-variant override that would force `debuggable="false"` regardless of this literal manifest value: a genuinely open conditional, not a hypothetical one. Full reasoning in `exploitation/AND-MAN-001.md`.
- **Remediation:** Set (or confirm) `android:debuggable="false"` for the release build type, and verify no manifest-merger directive from a library or debug build variant reintroduces it: the MAN-01 fix ("false in release"). This finding is resilience-category (MASVS-RESILIENCE-2), and its own prosecutor case is explicit that a live JDWP attach "allows bypassing any purely client-side check the app might otherwise rely on... because a debugger can single-step past or directly overwrite the result of any such check in memory." Treat the manifest fix as necessary but not sufficient on its own: no sensitive action in this app (above all, money transfers) should rely solely on a client-side gate that a debugger-attached process could falsify or skip: pair the manifest fix with independent **server-side** re-verification of authentication/authorization state for any sensitive operation, rather than trusting whatever state a connected client reports. *(Note on attribution: this app's own `resilience-anti-tamper-auditor` specialist was skipped for this engagement (per `target-profile.md`, there was no code or running app available for it to examine), so the client-side-vs-server-side framing above is this report's own synthesis of the prosecutor's attack-path reasoning, not a verbatim carry-forward of that specialist's `notes` field, which doesn't exist for this finding. See the handback note to this report's requester for the same caveat.)*

#### Static-only candidates not escalated to the panel (included here for completeness)

The two findings below carry Medium/High `severity_initial` ratings from `android-manifest-auditor` but were **never sent through prosecutor/skeptic review** in this engagement: a deliberate scoping choice for this demo walkthrough (see Appendix C), not a quality judgment. They are listed under Potential rather than Informational because their specialist-assigned severity is not informational in character; the badge/status shown is `Candidate`, not panel-reviewed `Potential`.

##### AND-MAN-004: AccountProvider exported with no permission, no path-permission, no URI scoping *(Candidate, not panel-reviewed)*
- **Severity (severity_initial):** High **Attacker model:** other-app **MASVS:** MASVS-PLATFORM-1, MASVS-STORAGE-1
- **Description:** `.data.AccountProvider` is declared `android:exported="true"` with authority `com.vulnbankdemo.app.provider` and no child elements at all (`extracted/AndroidManifest.xml:35-38`): no `android:readPermission`/`writePermission`/`permission`, no `<path-permission>`, no `android:grantUriPermissions` scoping, and a single flat authority with no path segmentation.
- **Attack path:** Any installed app can issue a `ContentResolver` `query()`/`insert()`/`update()`/`delete()` against `content://com.vulnbankdemo.app.provider` with no permission held, reaching `AccountProvider`'s implementation: not present in this fixture, but the class name implies account/financial data.
- **Evidence:** Static: `extracted/AndroidManifest.xml:L35-38`. Dynamic: `adb shell content query --uri content://com.vulnbankdemo.app.provider` against device `84f7a024` returned `IllegalStateException: Could not find provider: com.vulnbankdemo.app.provider`, confirming the provider is absent on-device because the package is not installed; the underlying read/write/injection question remains entirely unverified.
- **What would move this forward:** Escalation to the adversarial panel to test the attacker-model and severity claims the way AND-MAN-001/003 were tested, plus the provider's actual implementation code (or an installed build) to determine what data is actually returned/mutated and whether raw-SQL injection via `selection`/`sortOrder` parameters is possible.
- **Remediation:** Add `android:readPermission`/`writePermission` (or narrower per-operation `<path-permission>` entries) tied to a signature-level custom `<permission>`; set `exported="false"` if no external app genuinely needs this data; once implementation code exists, confirm parameterized queries are used throughout.

##### AND-MAN-002: android:allowBackup="true" with no backup-content restriction *(Candidate, not panel-reviewed)*
- **Severity (severity_initial):** Medium **Attacker model:** physical **MASVS:** MASVS-STORAGE-2
- **Description:** `<application android:allowBackup="true" ...>` with no `android:fullBackupContent` and no `android:dataExtractionRules` anywhere in the manifest (`extracted/AndroidManifest.xml:7-13`).
- **Attack path:** `adb backup`/cloud auto-backup extraction of the app's private data directory (SharedPreferences, SQLite DBs, files) on a physically-accessible, unlocked, debugging-enabled device.
- **Evidence:** Static: `extracted/AndroidManifest.xml:L7-13`. Dynamic: `adb backup -noapk com.vulnbankdemo.app` against device `84f7a024` triggered the device's interactive `BackupRestoreConfirmation` dialog, which the operator deliberately did not blind-tap through (the package was already confirmed not installed, and the device is shared with unrelated, out-of-scope apps visible during recon). The dialog was cleanly dismissed via `KEYCODE_BACK`, verified via `dumpsys activity activities` that the device returned to its prior foreground state with no backup produced and no app data touched.
- **What would move this forward:** Escalation to the adversarial panel, plus confirmation from a storage/crypto review that session tokens or cached account data are actually persisted locally and unencrypted: the finding's own notes state severity would rise on that confirmation. That specialist (`storage-crypto-auditor`) was skipped for this engagement because no storage/crypto implementation code exists in this fixture.
- **Remediation:** Add `android:fullBackupContent` (pre-API 31) or `android:dataExtractionRules` (API 31+) excluding session tokens and cached account data from backup, or set `allowBackup="false"` if there is no legitimate backup/restore use case for this app.

## Informational / hardening observations

- **AND-MAN-005: No `<uses-sdk>` declared; min/targetSdkVersion undeclared** (ref `MAN-12`). No `<uses-sdk>` element exists anywhere in the 42-line manifest, so `minSdkVersion`/`targetSdkVersion` cannot be read from this artifact, which matters for SDK-version-gated platform defaults (cleartext-traffic, exported defaults, backup policy) a downstream reviewer might otherwise assume. Kept low-severity/informational because this is a confirmed hand-authored fixture rather than evidence of a real shipped build lacking these values (unusual for a real Play Store release, since Play Console enforces a minimum `targetSdkVersion`). **Fix:** declare `minSdkVersion`/`targetSdkVersion` explicitly via `<uses-sdk>` (or verify the real `build.gradle` sets them), and re-check if a genuine build artifact is ever supplied for this target.
- **AND-MAN-006: Exported-component inventory (IPC surface map)** (ref `MAN-04`). Not an independently exploitable finding: a complete enumeration of all three declared components (`LoginActivity`, exported but benign/expected as the `LAUNCHER` activity; `TransferMoneyActivity` and `AccountProvider`, both already covered individually above) logged so downstream specialists have the full surface map rather than re-deriving it. **Fix:** none required; informational record only: any future specialist pass (`android-ipc-ui-auditor`, `taint-flow-analyst`) should consult this inventory rather than re-enumerating it.

**Third-party SDKs**: undeterminable. No `build.gradle`, no dependency lockfile, no embedded `.jar`/`.aar`/`.so`, and no SDK-characteristic `<meta-data>`/`<service>`/`<provider>` entries anywhere in the manifest. Treated as **zero evidence either way**, not "no third-party SDKs."

## Appendix C: Methodology & limitations

**Phase 2 (static) specialist coverage.** `target-profile.md`'s "Recommended Phase 2 specialist subset" names three specialists to run against this target out of the skill's 13: `android-manifest-auditor` (full remit, the primary specialist for this manifest-only target), `android-ipc-ui-auditor` (scoped to manifest-level exposure analysis of the two unguarded exported components), and `deeplink-clipboard-auditor` (scoped to its `DLK-01..08` sub-check only, for the `vulnbank://transfer` deep link; its clipboard sub-scope explicitly skipped for lack of code). **All six findings in `findings/findings.jsonl` are attributed solely to `android-manifest-auditor`.** There is no record anywhere in this engagement directory of output from `android-ipc-ui-auditor` or `deeplink-clipboard-auditor`: this report cannot determine whether they ran and found nothing to add, or did not run at all, and states that ambiguity plainly rather than implying full coverage of the recommended subset. The remaining ten specialists (`ios-plist-entitlements-auditor`, `ios-platform-attack-auditor`, `storage-crypto-auditor`, `taint-flow-analyst`, `webview-security-auditor`, `oauth-oidc-auditor`, `resilience-anti-tamper-auditor`, `network-backend-auditor`, `supply-chain-framework-auditor`, `business-logic-auditor`) were explicitly and deliberately skipped per `target-profile.md`, each with a stated reason tracing back to the same root cause: this fixture supplies only a plaintext `AndroidManifest.xml`, with no APK/AAB, no DEX, no source tree, and no `build.gradle` for any of them to examine.

**Phase 3 (dynamic) coverage.** A real, connected, authorized Android device (`84f7a024`, Xiaomi Redmi "sweetin", Android 11/SDK 30, production `user`/`release-keys` build) was genuinely available and genuinely used, not merely assumed present. `findings/dynamic-session-log.md` documents every command attempted. However, **dynamic confirmation of actual app behavior did not occur for any finding**, because there is no installable build of VulnBank for this device to run: every `reproduction_dynamic` command any finding proposed (`run-as`, `am start` on the deep link, `content query` on the provider, `dumpsys package`, `adb backup`) was executed verbatim and failed in the single, consistent, expected way (package/provider/activity not found), confirming the fixture's "no installable artifact" premise rather than confirming or refuting any manifest-level exposure claim. Hooking, fuzzing, MITM, resilience-bypass, and biometric-gate testing (dynamic method steps 3–8) were not attempted, each for the same reason: there is no running app process for any of them to target. State this plainly rather than letting the device's presence imply full dynamic coverage; it does not, for this target.

**Phase 4 (adversarial exploitation panel) coverage.** Of the six findings, only **AND-MAN-001** and **AND-MAN-003** were escalated to the full prosecutor/skeptic/orchestrator panel (`exploitation/AND-MAN-001.md`, `exploitation/AND-MAN-003.md`, two independent skeptic instances each). **AND-MAN-002, AND-MAN-004, AND-MAN-005, and AND-MAN-006 were never escalated**: a deliberate scoping choice for this demo walkthrough, not an oversight, and this report's Step 2 fallback rule (use each finding's own `severity_initial`/`status` in place of a never-set `final_severity`) was applied to all four accordingly.

**Tools actually used.** `adb` (Android Debug Bridge version 1.0.41, Version 35.0.2-12147458) was used directly against the connected device for every Phase 3 command above. `apktool`, `jadx`, and `aapt2` are present on the analysis machine's PATH but were **not used**, because the input artifact is a single plaintext, already-decoded `AndroidManifest.xml`: there is no binary AXML, no DEX, and no compiled resources for any of these tools to operate on; running them would do nothing useful.

**Out of scope per `scope.md`.** Everything beyond `AndroidManifest.xml` review, explicitly: "Out of scope: everything else, since no real code exists for this fixture."
