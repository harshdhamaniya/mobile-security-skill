# Severity & Confirmation Rating

This is the decision rule the `exploit-verifier-prosecutor` and `exploitability-skeptic` agents apply to every candidate finding, and the gate `report-synthesizer` enforces before a finding may appear in the report as **Confirmed**. The goal is to stop "theoretically missing a sanitizer" from being reported with the same weight as "I ran this and stole the token."

## Rating ladder

| Rating | Meaning | Required evidence |
|---|---|---|
| **Confirmed** | The attack path is real and exploitable by the stated attacker model, right now, in this build. | Prosecutor's case stands AND at least one of: (a) dynamic PoC evidence from `dynamic-runtime-verifier` or the panel itself (hook output, captured traffic, extracted secret, crash with controlled input), or (b) an unambiguous static proof where reachability and the absence/inadequacy of every claimed sanitizer are directly visible in code with no conditional the skeptic can plausibly argue closes the gap. AND the skeptic's refutation attempt failed on its merits (see below). |
| **Potential** | Plausible and worth fixing, but the panel could not fully close the loop: reachability is static-only and a device/build to dynamically confirm wasn't available, or a sanitizer exists but its adequacy is debatable, or the attacker model requires a precondition (e.g. rooted device, user installs a second malicious app) that is realistic but unverified in this engagement. |
| **Informational** | Best-practice deviation with no credible attacker model, or a resilience/anti-tamper gap on an app with no high-value asset (see `advanced-attacks.md` section C note: resilience is defense-in-depth, report absence as Low/Info unless the app protects banking/DRM/payment-grade assets). |
| **False Positive** | Skeptic's refutation succeeded: sanitizer is adequate, path is unreachable, or the "vulnerability" is standard platform behavior. Keep it in the record with the rebuttal. Don't delete it: it's useful to show what was checked. |

## Severity (impact, independent of confirmation status)
Rate `critical | high | medium | low` using standard impact x likelihood judgment, informed by:
- **Attacker model** from the finding schema: `remote` > `other-app` > `physical` > `local-root` > `none`, all else equal. A remote-exploitable bug is worse than one needing a rooted device.
- **Asset sensitivity**: auth tokens/credentials/payment data/PII/crypto keys > app-internal state > cosmetic/DoS.
- **Blast radius**: single account vs. account-takeover-at-scale vs. local-only.
- Use CVSS-like judgment but don't force a CVSS score unless the engagement asks for one; MASVS-flavored qualitative severity is the default for mobile audit reports.

Severity and confirmation status are independent axes. A `critical` finding can be `potential` (huge impact if true, but not yet proven reachable), and a `low` finding can be fully `confirmed`.

## The adversarial gate, concretely
1. **Prosecutor** writes the strongest honest case: concrete attacker precondition, step-by-step path from the stated attacker model to the sink, and what evidence already in `findings.jsonl`/`evidence/` supports each step. No evidence invention. If a step isn't backed by something in the record, the prosecutor must say "this step is asserted but unverified" rather than paper over it.
2. One or more **skeptic** instances independently try to refute: Is there a sanitizer the prosecutor missed? Is the attacker model wrong (e.g. this actually needs physical+root, not remote)? Does a platform mitigation (e.g. scoped storage, `FLAG_IMMUTABLE` default on newer targetSdk, ATS) already close this on the versions in scope? Is the "vulnerability" actually intended/documented behavior? Each skeptic returns a verdict: `refuted` (with the specific reason) or `stands` (explicitly state what they checked and couldn't knock down).
3. **Decision rule: evidence-primacy, not vote-counting.** Run at least 2 independent skeptic passes (3 for anything the prosecutor marks `critical`/`high`). A skeptic's `refuted` verdict is **well-evidenced** only if it cites a specific fact (a code line, a platform/SDK-version default, a control) that genuinely breaks a step in the prosecutor's path, *and that the prosecutor's case did not already address*. A refutation that just re-asserts something the prosecutor already accounted for ("but there's a sanitizer," when the prosecutor already explained why that exact sanitizer doesn't apply here) is a re-tread, not well-evidenced: treat it as weak.
   - **Any single well-evidenced `refuted` wins, no matter how many skeptics returned `stands`.** This is the rule that actually settles the hard case: 2-of-3 `stands` does not outvote 1 well-evidenced `refuted`. Evidence beats count unconditionally, not as a mere tiebreaker. Rate **False Positive** if the well-evidenced refutation shows the path is fully closed, or **Potential** if it raises a real doubt (an unverified precondition, an edge case) without fully closing it.
   - If no skeptic returns a well-evidenced `refuted`, at least one returns `stands` with specific checks actually performed (not just "looks fine"), and the dynamic-or-unambiguous-static evidence bar from the Rating ladder above is met -> **Confirmed**.
   - If every skeptic returns `refuted` but none is well-evidenced (all just assert doubt with no specific defeating fact), that is *not* a path to Confirmed either. It's a sign the case needs sharper scrutiny. Rate **Potential** and, if practical, run one more skeptic pass or request dynamic confirmation rather than forcing a label either way.
   - There is deliberately no vote to count and no numeric tie to break: one specific, checkable fact outweighs any number of unspecific ones, in either direction.
4. Record the full exchange in `exploitation/<finding_id>.md`: prosecutor's case, every skeptic's verdict and reasoning, and the specific fact (if any) that decided it. This transcript is part of the deliverable; a reader must be able to see *why* something was rated Confirmed, not just the label.
5. **Who writes the final label, and where.** The prosecutor and skeptic agents are deliberately scoped to `Read`/`Grep`/`Glob`/`Write`-into-`exploitation/` only (see their own files' "Discipline" sections); neither one edits `findings.jsonl`. Once a finding's skeptic passes are complete, the **orchestrating session** (whoever is running `SKILL.md`, not a subagent) applies the rule above to the finished transcript and writes `status` and `final_severity` into that finding's record in `findings.jsonl`, per `finding-schema.md`. `severity_initial` is never overwritten; `final_severity` is a separate field precisely so the specialist's original call stays on the record alongside the panel's. This hand-application step is mechanical (it applies this document's rule to a transcript that already fully exists), not a fresh judgment call, so it doesn't need its own subagent.
6. If genuinely nothing above resolves cleanly (for example, a well-evidenced `refuted` and a well-evidenced `stands` that address *different, non-contradicting* steps of the same path), rating is **Potential** by default. Ambiguity never rounds up to Confirmed.

## Anti-patterns to avoid (both prosecutor and skeptic)
- Prosecutor inflating severity by assuming the *worst possible* attacker model instead of the one actually supported by the evidence (e.g. claiming "remote" when the path really requires a second malicious app already installed, i.e. `other-app`).
- Skeptic reflexively downgrading everything to avoid conflict. A skeptic that never lets anything through "stands" is as useless as a prosecutor that confirms everything. Both must be able to point to the specific line/behavior driving their verdict.
- Treating "the obfuscator/ProGuard hides it" or "attacker would need to decompile first" as a mitigation: per `storage-crypto.md` CRY-13, static recoverability by any attacker willing to decompile is the baseline assumption for a mobile app; obfuscation is not a control.
- Treating resilience controls (root/debugger/Frida detection) as sufficient on their own. Per `advanced-attacks.md` section C, these only count as mitigating if paired with server-side verification; a client-only boolean check is not a sanitizer for anything.
