This section is intentionally prose, not a numbered checklist: these flaws are app-specific and require understanding what the app's flows actually *mean*, not grep-matching a pattern. Read `target-profile.md` and every other specialist's findings so far before starting; this agent benefits most from running later in Phase 2, once the attack surface and other findings give you concrete flows to reason about.

## Scope and method
For each theme below, ask: does this app have this flow at all, and if so, what would abusing it actually get an attacker?

- **Client-side trust of server-controlled values**: does the client enforce price, role, feature-flag, or entitlement state locally in a way that matters if the attacker simply calls the backend directly or patches the client? (This overlaps `network-backend-auditor`'s ADV-81 authZ findings and `supply-chain-framework-auditor`'s ADV-107 IAP note; if you find the same root cause, cross-reference rather than re-file.)
- **Race conditions**: double-spend or multi-redeem flows, such as promo codes, wallet balance deduction, limited-inventory purchases, or "redeem once" rewards. Look for a check-then-act pattern (check balance/eligibility, then separately perform the action) with no apparent locking or idempotency token. This is inherently a concurrency bug class that's hard to prove without firing concurrent requests, so if you can't test it live, write it as a design-level `potential` finding naming the specific flow and why the code pattern looks vulnerable to a race.
- **IAP receipt forgery/replay**: beyond Unity's client-trust pattern (owned by `supply-chain-framework-auditor` for that framework), does *any* platform's purchase flow accept a receipt/token without server-side validation against the platform's verification API, or without checking it hasn't been used before (replay)?
- **Jailbreak-store/sideload bypass (Lucky-Patcher-class)**: for apps with paid features, is there a local-only check that a patched APK/binary can simply flip? This is the client-trust theme again, applied specifically to monetization.
- **License checks**: same pattern for non-consumer/enterprise licensing if present.
- **Promo abuse**: can a promo/referral code be reused beyond its intended limit by manipulating client-visible state (device ID reset, account recreation, request replay)?
- **Session fixation / concurrent sessions**: does logging in on a second device invalidate the first session's tokens, or can both run indefinitely? Is a pre-auth session token ever reused post-auth without rotation (classic fixation)?
- **Offline-mode data tampering and sync conflicts**: for apps with an offline/local-first mode, can locally-tampered data (balances, flags, records) be synced back to the server as authoritative when connectivity returns, with no server-side revalidation?
- **Deep-link-triggered actions**: does any deep link trigger a sensitive action (not just navigate) with no confirmation step? This is the same theme as `deeplink-clipboard-auditor`'s DLK-03 ("link parameters trigger sensitive actions... without confirmation"). If they've already filed it, don't re-file. If you spot a business-flow consequence (fund movement, entitlement change) that they may have under-weighted as a navigation issue rather than a business-logic one, flag that connection explicitly in `notes`.
- **QR/NFC payload trust**: does scanning a QR code or tapping an NFC tag trigger an action based on unvalidated payload content (payment amount, deep-link action, config change)? This overlaps `deeplink-clipboard-auditor`'s DLK territory when the payload is a URL, so cross-reference.
- **Biometric enrollment changes**: does adding a new fingerprint/face invalidate keys bound to the old biometric enrollment (as it should, per `storage-crypto-auditor`'s STO-16/CRY-45 notes), or does the app silently keep trusting a session/key across an enrollment change it should have treated as a trust boundary?
- **Device-binding/migration flows and account recovery**: when a user migrates to a new device or recovers an account, is there a window where the recovery flow's own trust requirements are weaker than normal login (a common target for account-takeover)?

## Output
Append to `engagement-<slug>/findings/findings.jsonl`, prefix `BOTH-LOGIC-NNN`. These findings are frequently `potential` rather than `confirmed` by nature (many need live concurrent-request testing or a second real account to prove). Don't inflate confidence to compensate: write a precise `reproduction_dynamic` describing exactly what test would confirm it (e.g. "fire N concurrent redeem requests for the same promo code from two sessions and check if more than one succeeds") so the exploitation panel or a follow-up dynamic session can act on it directly.
