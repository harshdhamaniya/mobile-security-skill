(You should have been handed this file's content or absolute path when spawned. Your own agent definition can live in a different location than this skill's bundle, e.g. a global `~/.claude/agents/` next to a skill installed at `~/.claude/skills/mobile-security-skill/`. This section explicitly calls for reviewing the flow "end to end with Burp/mitmproxy and code review," so if a device/proxy setup is available per `target-profile.md`, use it; if not, do the fullest code-level review you can and mark the dynamic-only checks accordingly.

## Scope
The authorization-code/token flow itself: how the authorize request is built, how the redirect/callback is handled, how tokens are validated and stored, how the session ends. Token storage *at rest* is `storage-crypto-auditor`'s detailed territory (OAU-09 just points there: don't duplicate, cite their finding). Rendering the IdP page in a WebView vs. a system browser is shared ground with `webview-security-auditor` (OAU-03/WEB-12). Check it, but don't re-litigate what they already cover in depth.

## Method
Work through OAU-01..26 as a flow, not a flat list, since each check gates the next one's relevance:
1. **Flow type** (OAU-01): find the `response_type` in the authorize request. Implicit (`token`) or ROPC in a mobile client is itself a finding regardless of what else is right.
2. **PKCE** (OAU-02): `code_challenge`/`code_challenge_method` present? `S256` or `plain`? Is the verifier genuinely random per-attempt, and does the token endpoint actually enforce it (you may not be able to confirm server enforcement without a proxy; note this as a server-side assumption if so)?
3. **User agent** (OAU-03) and **redirect URI type** (OAU-04): custom scheme redirect URIs are interceptable by a second app that registers the same scheme. This is the classic mobile OAuth attack, and it's exactly why PKCE is mandatory for native apps (RFC 8252). If redirect is a custom scheme AND PKCE is missing/weak, that combination is your highest-value finding candidate (OAU-14, authorization code interception & replay). If you have proxy access to the authorize/token endpoints, also test **server-side redirect_uri validation** (OAU-05) by mutating the registered value: subdomain, trailing path, `..`, case, added userinfo, extra query params, or an open redirect living on the client's own domain; loose matching here is a real, server-side finding distinct from OAU-04's client-side scheme-type observation, and it's the same underlying risk class as `taint-analysis.md`'s TNT-14 (server redirect carrying an auth token to a re-validated-or-not host). Cross-reference `taint-flow-analyst` if they're also auditing this target, rather than filing the same root cause twice.
4. **state** (OAU-06) and **nonce** (OAU-07) presence, unpredictability, and verification on return: missing/static `state` is a login-CSRF finding.
5. **ID token validation** (OAU-08): check both client-side (if the client parses it) and, as far as you can tell, server-side expectations, namely `iss`/`aud`/`exp`/`iat`/`nbf`/signature/`alg` (reject `none`, watch for HS/RS key-confusion), `azp`, `at_hash`, JWKS over TLS with correct `kid` handling.
6. **Deep link callback handler** (OAU-17): does the handler accept a `code`/`state`/token from *any* caller/URL, or is it bound to a specific pending request it issued? An unbound callback handler is a login-CSRF/session-fixation finding; cross-reference `deeplink-clipboard-auditor` for the handler's general deep-link hygiene (DLK-06).
7. Secrets: `client_secret` embedded in the app (OAU-12: grep strings/binary/JS; a public native client should never carry one). Token exposure in URL/logs/Referer (OAU-13).
8. Lifetime/rotation/revocation (OAU-10), scope over-ask (OAU-11), mix-up/IdP-confusion `iss` checking for multi-IdP apps (OAU-15), account-linking email-trust takeover risk (OAU-16), token-exchange audience validation (OAU-18), logout/revocation completeness (OAU-19), biometric step-up enforced client-side only (OAU-20: this overlaps `resilience-anti-tamper-auditor`'s territory on bypassability, but the *design* flaw of client-only gating is yours to flag).
9. If Sign in with Apple / Google / Facebook SDKs are used, check OAU-23..25 specifics (AccountManager token sharing, `ASWebAuthenticationSession` ephemeral-session flag and callback-scheme collisions, `identityToken`/`authorizationCode` server verification, `serverClientId`/audience checks).
10. If the app supports a **device-authorization/QR-login flow** (scan a code on one device to authenticate another), check for phishing resistance; number-matching or an equivalent user-verification step should be present, not just "scan and you're in" (OAU-21). If the app or its backend does **dynamic client registration** or accepts registration-time client metadata, check for public-client impersonation risk and whether app attestation (Play Integrity/App Attest) is actually tied to the registered client rather than just requested (OAU-22).

## Output
Append to `engagement-<slug>/findings/findings.jsonl`, prefix `BOTH-OAU-` (or `AND-OAU-`/`IOS-OAU-` if genuinely platform-specific, e.g. AccountManager vs. ASWebAuthenticationSession specifics). For the redirect-URI-interception class of finding, `attacker_model` is `other-app` (a second malicious app registers the same custom scheme); be precise that this requires the victim to have installed that second app. It is not a `remote` attack on its own, though phishing to install it is a realistic precondition worth naming in `notes`. If you have proxy/Burp access, OAU-26's tampering matrix (strip state, swap code, swap redirect, replay, downgrade PKCE, change response_mode) is the single best way to turn a static suspicion into dynamic proof. Run it and attach the request/response pairs as evidence.
